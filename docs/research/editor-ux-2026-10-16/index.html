Make the game object the starting point.

Crucible needs a coherent editing workflow, not another collection of prettier tool panels. This report compares established editors, traces problems to the current implementation, and specifies how to evaluate a replacement.

Research and proposed requirements. The redesign described here is not implemented or user-tested. Target: the CoA client, server and core. Baseline: 52b826d.

The main finding

The current interface frequently asks the user to translate a game problem into a file, table, record identifier or deployment operation before they can edit it. “Fix this floor” becomes “find the ADT, identify the texture layer and its MTEX entry.” “Change this sword” crosses copying, appearance resolution, SQL editing and client synchronization. Those are legitimate internal operations; making the user assemble them is the usability failure.

The strongest candidate direction is a shared content document: find or select an item, creature, spell, class or place; edit relevant properties; see the effect; review the actual affected destinations. This is an inference from the comparisons and code audit below. It is not evidence that one particular arrangement of panels will suit every task.

Keep the technical depth. Raw tables, custom fields, exact IDs, source comparison and scripts must remain reachable. Simpler entry should remove unnecessary translation, not remove capability. The default experience and the expert view should edit the same draft through the same validation and target adapters. Unity inspection, RPG Maker’s game concepts, TEdit’s contextual editing and progressive disclosure inform this direction.

A resizable three-pane shell alone will not solve this. Crucible already has splitters, preview surfaces and workflow-oriented documentation. The missing piece is consistency across discovery, selection, editing, undo, saving and application. A friendly control cannot compensate for an unimplemented writer or an unknown CoA field.

What was actually researched

The source ledger distinguishes official documentation, primary code, published screenshots and UX/accessibility guidance. Patterns were selected for their relevance to Crucible’s tasks, not because a tool is popular or its screenshot looks attractive.

  • External evidence: read the linked editor manuals, project material and UX guidance. Inspected the published Keira3 item screenshot and WoW Database Editor game-view screenshot. The latter labels itself 2021.2; neither screenshot is a current installed-app test.
  • Local evidence: inspected the main shell, item creation/workbench, texture and map workspaces, setup, responsive split layout, document undo, Class Studio spellbook/bridge and relevant CoA/asset services. Source links in the audit use the exact baseline commit.
  • Capture limitation: isolated item, texture, map and setup views were rendered at 1440×900 and 1024×768 without global input or game writes. Their offscreen render had unreliable tab/text presentation; those captures are excluded from visual defect evidence. Source-backed terminology and workflow findings do not depend on them.
  • Not performed: hands-on trials of every external editor, novice participant testing, live SQL editing, game deployment, a final visual design, or a full Crucible accessibility audit. Interaction feel and discoverability remain hypotheses until observed in use.

Published manuals describe intended behavior, not universal usability. A reference is useful even when part of its interface is a poor fit. The comparison explicitly separates observed behavior, proposed adoption, rejected patterns and a validation question. Failed page fetches and third-party search snippets are not used to establish technical behavior. No external editor source or artwork is copied into the product.

The primary project pages establish Noggit3 and Noggit RED separately; old source is not labelled current RED behavior. Terrasavr’s manual includes legacy browser guidance. PKHeX’s older tutorial is paired with release notes documenting newer feedback changes. These version limits are retained in the evidence ledger.

Docking and free placement are different jobs

Application panels need movable docks, split sizing, optional floating, maximize, close/reopen and saved layouts. The class-design workspace additionally needs free board placement with the requested grid and snapping. Both should persist, but they should not share a model that treats closing a panel as deleting the content. A visible Layout menu must recover every hidden panel and restore defaults without losing edits. Every major pane must be adjustable; a useful default is still required.

Beginner access without a separate crippled mode

Prefer task-relevant controls first and named secondary sections such as Advanced fields, Source values and Generated output. Avoid global Beginner/Expert modes that silently change behavior or hide the location of a setting. A known field should keep its meaning between views; unknown custom data stays intact and inspectable. Guided entry can help a first edit, but repeated edits should not require a tutorial or multi-page wizard. This is a proposed application of progressive disclosure.

A change can be saved yet unapplied, partly applied yet unverified, or blocked by a source that changed externally. Those states need concise names and a clear next action. They should not become permanent warning walls. Dismiss a notification without erasing its underlying issue from Problems. PKHeX’s unsaved-editor warning and Terrasavr’s file handoff illustrate why the boundaries matter.

How the interaction should feel

Predictable, responsive and recoverable are testable properties. “Modern,” “clean” and “intuitive” are not sufficient acceptance criteria. The following requirements are proposed for Crucible; references motivate them, but do not prove their implementation or effectiveness here.

The 100 ms feedback budget is a proposed engineering target, not a measured result. Test it separately from indexing or decoding time. Likewise, WCAG guidance informs the browser surface and analogous desktop interaction tests; this report does not claim whole-application WCAG conformance. Response-time guidance, drag alternatives, target size and status announcements provide concrete references.

Rework the workflow at the correct layer

Do not begin with a color palette, a new sidebar or a framework migration. First prove the content/draft contract and two real editing jobs. The current app is Avalonia with a shared Class Studio frontend; no evidence gathered here justifies rewriting all readers or changing that technology merely to improve appearance.

The existing CrucibleContentProjectService already owns project identity, target profile and reserved content IDs. Extend and integrate that foundation where appropriate; do not introduce a competing project format merely to support new panels. The missing common document/draft behavior must be assessed separately from the project container that already exists.

Feature preservation is a release requirement

Before replacing a workspace, inventory its operations: opening/search, creating/cloning, references, custom fields, previews, batch behavior, validation, exports, application, recovery and keyboard access. Map each to the replacement, an explicit advanced route, or a clearly documented unsupported operation. This prevents the redesign from becoming a smaller editor that happens to look simpler.

Retain existing source fingerprinting, exact-schema checks, CoA archive policy, unknown-field preservation and transaction boundaries. Do not auto-fix an ambiguous source, silently invent a default or flatten custom class IDs into stock classes. Unknown semantics are an adapter problem, not something an explanatory tooltip can repair.

As each vertical workflow is verified, replace its old UI and remove the superseded interaction path. Keep existing formats and saved designs migratable. Avoid permanently maintaining a “new friendly UI” and an unrelated legacy editor with separate draft models. Export-only capabilities must keep honest labels until their corresponding writers and deployment checks exist.

How to prove it is usable

The user’s “no questions” goal means ordinary jobs should not require knowing table names, asking the developer, or reading a technical manual. No responsible research report can guarantee every novice will understand every advanced editing task. Treat a request for help during a common task as actionable evidence, not as user failure.

Run short, observed task sessions with people unfamiliar with Crucible, including basic computer users and experienced WoW modders. Give an outcome, not directions containing button names. Ask them to say what they expect; do not teach the route. Separate an exploratory think-aloud session from a timed performance session. Record assistance, wrong turns, lost drafts, mistaken scope, and whether they understand where the change was saved. Thinking-aloud method.

Proposed acceptance gates, not measured results

  • For common single-object tasks: no external ID/file/table lookup, no facilitator instructions, no loss of work and no unintended game changes. Time targets should be set after the first observed baseline, rather than invented here.
  • For all tasks: user can identify the selected object, affected scope, current save/application state and next action.
  • For recovery: undo restores the expected draft; errors retain edits; a closed panel is recoverable; a failed/partial apply is never displayed as complete.
  • For layout: verify 1024×768, 1440×900 and 1920×1080 effective viewport sizes, 100/150/200% scaling as applicable, larger text and monitor changes. Default forms must not need horizontal scrolling for a few clipped pixels. Deliberately wide tables/canvases may scroll within their own surface.
  • For compatibility: include a custom CoA class, a spell supplied by an override, missing SQL, conflicting patches and an unknown custom column. A stock Wrath success must not stand in for CoA compatibility.
  • For testing claims: automated navigation, layout, reader and writer checks support correctness. They do not establish novice comprehension or subjective interaction quality. Human sessions remain pending.

Use the same tasks to compare the old and replacement flows. Avoid turning a small qualitative sample into a statistical success-rate claim. Fix recurring blockers and repeat with fresh participants so familiarity does not masquerade as improved design. Keep the findings in the repository with the tested build and actual observations.
